# Portal deployment

The portal uses Vercel for Next.js, Render for NestJS, Neon for PostgreSQL, and Upstash for Redis. Deploy the backing services and API before the web app so every URL is available when Vercel builds.

The committed `apps/scholark-portal-api/.env` contains local-development defaults. Deployment values belong in the ignored `apps/scholark-portal-api/.env.stage`; never replace the committed local file with production credentials.

## 1. Neon

Create a Neon project and database, then copy its **pooled** connection string. Set it as `MIKRO_ORM_DATABASE_URL` in Render. Keep the TLS query parameters supplied by Neon.

Run production migrations from a trusted shell before releasing an API version that requires schema changes:

```bash
NODE_ENV=stage pnpm --filter scholark-portal-api migration:up
```

## 2. Upstash

Create an Upstash Redis database and copy the native Redis TLS URL into Render as `REDIS_URL`. It must have this shape:

```text
rediss://default:<password>@<host>.upstash.io:6379
```

Do not use `UPSTASH_REDIS_REST_URL` or the REST token; the API uses the Node Redis protocol client.

## 3. Render

Put only values that differ from local development in `apps/scholark-portal-api/.env.stage`. Generate a complete, expanded dotenv payload by running:

```bash
pnpm --silent --filter scholark-portal-api env:export:stage
```

Copy the output into **Environment > Add from .env** in the Render dashboard, then create a Blueprint from the repository's `render.yaml`. The command overlays `.env.stage` on the committed `.env`, expands references such as `${WEBSITE_BASE_URL}`, and omits empty values so they do not override Blueprint defaults. Render cannot read the ignored file directly; the import stores the merged values as encrypted service environment variables. Values generated by the Blueprint may remain in Render instead of being duplicated in `.env.stage`.

The Blueprint sets `NODE_ENV=stage`. NestJS and MikroORM CLI therefore resolve files in this order: `.env.stage.local`, `.env.stage`, `.env.local`, then the committed `.env`. Environment variables supplied by Render take precedence over every file.

Use these URL values after the Vercel project exists, replacing `<web-origin>` with its HTTPS origin and omitting trailing slashes:

| Variable | Value |
| --- | --- |
| `CORS_ORIGIN` | `<web-origin>` |
| `AUTH_CONFIRM_EMAIL_URL` | `<web-origin>/auth/confirm-email` |
| `AUTH_UPDATE_PASSWORD_URL` | `<web-origin>/auth/reset-password` |

Set `AUTH_CONFIRM_EMAIL_FROM` and `AUTH_RESET_PASSWORD_EMAIL_FROM` to valid sender addresses. Configure the optional `SMTP_*` variables for a production mail provider. Render supplies `PORT`; do not set it manually.

After deployment, verify:

```bash
curl --fail https://<render-service>.onrender.com/api/v1/health/alive
```

## 4. Vercel

Import the repository and select `apps/scholark-portal-web` as the project root directory. Keep the Next.js framework preset and pnpm defaults. Ensure Vercel includes files outside the root directory so the workspace dependency under `packages/ui` is available.

Set these variables for Production and Preview as appropriate:

| Variable | Value |
| --- | --- |
| `NEXT_PUBLIC_API_BASE_URL` | `/api` |
| `API_SERVER_BASE_URL` | `https://<render-service>.onrender.com` |

The `/api` rewrite proxies browser requests through Vercel, keeping session cookies first-party. Server Components use `API_SERVER_BASE_URL` to call Render directly.

For preview deployments, either use a stable custom preview domain or add the preview origin to Render's comma-separated `CORS_ORIGIN`. Production should use an exact origin rather than a wildcard.

## 5. Release check

Verify registration, login, logout, password reset, and an authenticated profile request in a private browser window. Then inspect Render logs for database or Redis TLS errors and confirm the browser stores the secure session cookie on the Vercel domain.
